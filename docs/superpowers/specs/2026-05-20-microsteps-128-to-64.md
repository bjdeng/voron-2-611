# Stepper noise reduction — microsteps 128→64 + TMC Autotune

**Status:** Approved 2026-05-20 (Phase A originally; expanded to include Phase B). Implementation pending.
**Closes:** [#24](https://github.com/bjdeng/voron-2-611/issues/24)

## Background

All 6 mainboard steppers (X, Y, Z, Z1, Z2, Z3) currently run at `microsteps: 128` with `interpolate: False` and `stealthchop_threshold: 0` (always spreadCycle). This config was adopted from third-party forum advice with the stated goal **"quiet without losing steps"** — never empirically validated on this machine.

User's actual goal (clarified 2026-05-20): a quiet printer with no missed steps and no movement variation. The forum advice was a starting point; this spec validates whether it's actually optimal.

Three observations make the current config questionable:

1. **Klipper docs say 64 is acoustically equivalent to 128 with `interpolate: False`.** From `vendor/klipper/docs/TMC_Drivers.md:106-109`: "Typically, a microstep setting of 64 or 128 will have similar audible noise as interpolation, and do so without introducing a systemic positional error." The systemic error described in the same section only applies when `interpolate: True` — irrelevant here.

2. **MCU step-rate budget is tight at 128.** LPC1769 USB-limited to ~628k steps/sec per `vendor/klipper/docs/Benchmarks.md`. At `max_velocity = 450 mm/s`, CoreXY moves drive ~576k steps/sec across both X/Y motors at 128 microsteps — **~92% of MCU USB budget**. Currently zero `step_compress` warnings in klippy.log, so we're not hitting it, but margin is thin.

3. **TMC2209 driver waveform is not tuned for our specific motors.** The TMC2209's chopper parameters (`TOFF`, `TBL`, `HEND`, `HSTRT`, `PWM_FREQ`, `PWM_GRAD`) directly affect motor noise but are currently at Klipper defaults. The [TMC Autotune](https://github.com/andrewmcgr/klipper_tmc_autotune) extension computes per-motor optimal values from motor specs (inductance, resistance, rated current) and machine config — community reports 5-15% noise reduction on spreadCycle TMC2209 setups.

## Goal

Reduce stepper noise as the primary outcome, with MCU headroom as a useful side benefit. Both changes are reversible single-file edits — if either makes the printer worse, revert.

## Non-goals

- **stealthChop on X/Y.** Community consensus and Klipper's own warnings about mid-move mode switching make stealthChop on a high-accel CoreXY (10k mm/s²) X/Y a known risk. If Phase A + B don't satisfy quietness, stealthChop on Z motors (only) is a separate follow-up.
- **Lower microsteps (16, 32).** Klipper docs don't suggest these produce better acoustics; they may reintroduce stepper resonance noise that 64+ smooths out. If 64 underperforms vs 128, that's the moment to discuss going lower.
- **MMU steppers** (on EASY-BRD / SAMD21G18A). Different MCU, different step rate budget, and changes would invalidate MMU calibration.
- **Extruder** (on EBB / RP2040). Different MCU with much higher step rate headroom; extruder doesn't move at MCU-stressing velocities. TMC Autotune COULD theoretically tune the extruder driver too, but it's a different scope and the extruder is already quiet.

## Phase A: Microsteps 128 → 64

### Change

Six lines in `config/motion.cfg`:
- `[stepper_x] microsteps: 128 → 64`
- `[stepper_y] microsteps: 128 → 64`
- `[stepper_z] microsteps: 128 → 64`
- `[stepper_z1] microsteps: 128 → 64`
- `[stepper_z2] microsteps: 128 → 64`
- `[stepper_z3] microsteps: 128 → 64`

No other config changes. `rotation_distance`, `interpolate: False`, `stealthchop_threshold: 0`, `run_current`, `sense_resistor` all stay. Klipper computes step pulses as `(distance / rotation_distance) × full_steps × microsteps` automatically — no other tuning is invalidated by a microstep change.

**Restart impact:** `RESTART` (Python-side stepper config + a re-emit of TMC SPI/UART register writes; no MCU pin or kinematics change).

### Test sequence (~30 min)

**Phase A.0 — Baseline capture (before any change):**
1. Confirm printer is homed + QGL'd
2. Run `TEST_SPEED` macro **twice**. Note: subjective noise rating (1-5 scale), any abnormal sounds (clunks, screeches, missed-step clicks), final position diff reported by the macro
3. `ssh pi@mainsailos.local "grep -c step_compress ~/printer_data/logs/klippy.log"` → record baseline (expected: 0)

**Phase A.1 — Apply change:**
1. Branch → edit motion.cfg → local CI gates (`make refcheck && make test-py`)
2. PR + CI green → squash-merge → `/deploy-to-pi`

**Phase A.2 — Post-change verification:**
1. Home + QGL after firmware restart (clears homing state)
2. Run `TEST_SPEED` **twice**. Same observations as A.0
3. Quick test print: small benchy or Voron cube (~30 min). Visually inspect for surface artifacts vs typical prints
4. Post-print: `grep -c step_compress ~/printer_data/logs/klippy.log` → confirm zero

### Phase A success criteria (ALL must pass)

| Criterion | Pass threshold |
|---|---|
| TEST_SPEED skip check | Position diff < 0.1 mm (the macro's own default) |
| Subjective noise | ≤ baseline rating (equal or quieter) |
| Test print surface | No new ringing, ghosting, or layer artifacts vs prior prints |
| MCU step rate | Zero `step_compress` warnings in klippy.log post-change |

### Phase A rollback

Single revert PR restores 128 microsteps in all 6 sections. ~10 min total. No printer state to clean up — microsteps don't persist anywhere outside motion.cfg.

## Phase B: TMC Autotune installation + tuning

**Prerequisite:** Phase A complete (success or rollback). Phase B layers on top of whatever microstep setting wins Phase A, so we can attribute noise changes cleanly.

### Background

[TMC Autotune](https://github.com/andrewmcgr/klipper_tmc_autotune) is a third-party Klipper extension that auto-computes optimal TMC driver register values from motor specifications (`MOTOR_NAME`, current rating) and machine-specific constraints (max_velocity, max_accel). It runs at startup, reads motor specs from its own bundled motor database, and writes computed values into the TMC driver registers via UART (TMC2209 here).

Install pattern matches Happy-Hare + eddy-ng + shaketune: clone to home, symlink into `klippy/extras/`. Same "third-party install.sh sets up update_manager on Pi" pattern — already addressed by the deploy footgun mitigation work ([#87](https://github.com/bjdeng/voron-2-611/issues/87)).

### Change

1. **Pi install:** `wget -qO - https://raw.githubusercontent.com/andrewmcgr/klipper_tmc_autotune/main/install.sh | bash` (with sudo via stdin per [[sudo-via-stdin]] pattern)
2. **Vendor:** add `vendor/klipper-tmc-autotune` submodule (consistency with happy-hare, eddy-ng, shaketune)
3. **Repo:** add the `[update_manager]` block to `config/moonraker.conf` (don't let it get wiped on next deploy, per [#87](https://github.com/bjdeng/voron-2-611/issues/87))
4. **Repo:** add `[autotune_tmc stepper_*]` blocks to `config/motion.cfg` for each of the 6 mainboard steppers — references motor model name from autotune's bundled motor database

Motor model lookup needed: identify the steppers in this build. Voron-2 BOM defaults to LDO-42STH48-2504AC for X/Y and LDO-42STH48-2004MAH for Z. Need to verify against the actual installed motors before authoring the config.

**Restart impact:** `RESTART` after install (Python extension load + register writes via TMC UART).

### Test sequence (~30 min + 10 min for motor identification)

**Phase B.0 — Motor identification:**
1. Physically inspect the steppers (or check the build BOM in vendor/voron-2/Manual/) to identify the actual motor models on X, Y, Z×4
2. Verify the models are in `~/klippain_shaketune/motor_database.csv` (or whatever the autotune motor database file is — TBD pending install)

**Phase B.1 — Baseline capture (post-Phase-A state):**
1. Re-record subjective noise rating during TEST_SPEED — this is the new baseline (since Phase A may have changed it)

**Phase B.2 — Install + configure:**
1. Run install.sh on Pi (sudo via stdin per the established pattern)
2. Add vendor submodule + moonraker update_manager block + per-stepper `[autotune_tmc]` config — single PR
3. Deploy + RESTART

**Phase B.3 — Post-change verification:**
1. Check klippy.log for autotune startup messages confirming it ran successfully for all 6 steppers (no errors writing TMC registers)
2. Home + QGL
3. Run `TEST_SPEED` **twice**. Compare subjective noise to B.1 baseline
4. Quick test print (same model as Phase A test print for direct comparison)

### Phase B success criteria

| Criterion | Pass threshold |
|---|---|
| Autotune startup | klippy.log shows no errors writing TMC registers; all 6 steppers tuned |
| TEST_SPEED skip check | Position diff < 0.1 mm |
| Subjective noise | ≤ Phase A baseline (equal or quieter — failure mode is autotune making it worse) |
| Test print surface | No new artifacts vs Phase A test print |

### Phase B rollback

Remove `[autotune_tmc]` blocks from motion.cfg and the update_manager block from moonraker.conf. Optionally `ssh pi@mainsailos.local "rm -rf ~/klippain_tmc_autotune"` to fully uninstall. Restart picks up unmodified config.

The vendor submodule can stay even if we revert — it's just sparse-checkout source for grep. If the experiment is a clear failure, drop the submodule in a follow-up cleanup commit.

When closing issue #24:

Update CLAUDE.md "Known quirks" to remove the "Microsteps 128 (atypically high)" caveat. Add CLAUDE.md note about TMC Autotune being installed (mention update_manager in moonraker.conf).

**Phase A success, Phase B no-op or failure:** Comment with the data. Keep Phase A change; document Phase B as evaluated-and-rejected with the failure reason. CLAUDE.md update for microsteps; no autotune mention beyond a brief "tried, didn't help" line in the future-investigations log.

**Phase A failure:** Revert Phase A immediately. Decide whether to proceed with Phase B (autotune could still help even without microstep change) or shelve the whole investigation.
